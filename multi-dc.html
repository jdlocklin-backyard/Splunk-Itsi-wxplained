Multi-DC Fulfillment Network — Splunk ITSI

How a shared service outage cascades across two Distribution Centers and surfaces on a single executive dashboard

This infographic demonstrates multi-DC service modeling in Splunk ITSI. Two distribution centers (DC-East and DC-West) share centralized AWS services for order routing, inventory sync, and carrier API integration. When a shared service degrades, ITSI's dependency propagation reflects the impact across both facilities — with differential severity depending on each DC's carrier mix. Shared Service Dependencies: Order Routing, Inventory Sync, and Carrier API Gateway are standalone services depended on by both DCs. A shared service failure cascades into both branches of the service tree simultaneously.
Differential Impact: The same shared service failure can hit one DC harder than another. DC-West relies on FedEx — when the Carrier API Gateway's FedEx endpoint fails, DC-West shipping stalls while DC-East (UPS primary) sees only partial degradation.
Episode Correlation: When ITSI sees Shipping-East and Shipping-West degrade simultaneously alongside a Critical Carrier API Gateway, it groups all alerts into a single Notable Event Episode — preventing alert storms.
Automated Remediation: ITSI aggregate policies can open ServiceNow incidents and trigger Ansible playbooks — e.g., failover FedEx traffic to UPS at DC-West when the Carrier Gateway's FedEx endpoint fails.
Shared services are the key modeling insight. Order Routing, Inventory Sync, and Carrier API Gateway are standalone ITSI services. Both DC operations list them as dependencies — ITSI automatically computes cascading impact across both branches.
Entity scoping with facility dimension. DC-specific services filter KPI searches by facility=dc-east or facility=dc-west. Shared services use facility=shared. Same KPI definitions, different entity scope.
Episode correlation prevents alert storms. When ITSI sees correlated degradation across both DCs, it groups Shipping-East, Shipping-West, and Carrier API Gateway alerts into one episode, pointing operators to the shared root cause.
Automated remediation triggers. ITSI aggregate policies can fire ServiceNow incidents and Ansible playbooks — e.g., auto-failover FedEx traffic to UPS at DC-West when the Carrier Gateway degrades.
